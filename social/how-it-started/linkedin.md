# LinkedIn: How it started

Draft only. Mike schedules it himself.

A week ago I started an experiment: one AI assistant, and a rule that it would only suggest a new assistant once the same kind of request had come up two or three times.

By the next morning I had seven, each with one job and a written list of things it must never do. One tracked open work but couldn't build anything. One looked after my Windows PC and couldn't install drivers without my yes. One reviewed code and never applied its own fixes. One argued with another AI for a second round before reporting back.

By the end of the week I had nine. Today I deleted all of them and moved to one assistant, HQ, my main workbench. The public build log I'm writing is a byproduct of that work.

What I'm keeping:
• Evidence before structure. Don't add a role until the work shows a repeated need.
• One job per role, with written anti-jobs.
• Whoever writes code owns it. A separate checker reviews and never applies its own patch.
• Push any first answer for a second round, and list what's still unverified.
• Publish real problems and real fixes, not volume.
• If a step has no judgment in it, use code, not an AI.
• Don't underestimate context. Know how much one assistant can hold before another has to take over.
